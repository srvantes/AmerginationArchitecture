# Резервные копии и восстановление

Скрипты предназначены для Linux-сервера с Bash, Docker Compose v2 и утилитами
`sha256sum`, `flock`, `mktemp` из стандартной Ubuntu 24.04. Они используют
**только** `compose.production.yaml`. Запускайте из копии проекта на сервере.
Работающий PostgreSQL 17 и собранный образ приложения нужны заранее.
Для проверок и работы с архивами скрипты запускают временный сервис
`maintenance` из профиля `tools`: тот же образ и volume аватаров, но только
внутренняя backend-сеть, без опубликованных портов и фиксированного IP `app`.
Он позволяет проверить копию при ещё работающем приложении, не занимая его
сетевой адрес. Отдельно запускать этот сервис вручную не требуется.

## Что сохраняется

Каждая копия — отдельный каталог:

```text
20261022T120000Z-XXXXXXXX/
  database.dump       # pg_dump custom format: пользователи, миграции и все таблицы
  avatars.tar.gz      # файлы из volume avatars
  schema-version.txt # ревизия Alembic на момент копии
  backup-info.txt     # версия формата, время UTC, major PostgreSQL
  SHA256SUMS          # контрольные суммы четырёх файлов выше
```

Права новых каталогов и файлов ограничены `umask 077`. Сначала пишется каталог
`.partial-...`; он переименовывается в окончательный только после успешного
получения обоих снимков и контрольных сумм. Незавершённый `.partial-...` не
считается резервной копией. При ошибке он остаётся для диагностики.

Пароли не передаются через аргументы команд и не попадают в вывод скриптов.
`.env.production`, SMTP-пароль, TLS-данные Caddy и образы приложения в копию
**не входят**. Храните конфигурацию отдельно в защищённом хранилище; сохраняйте
версию исходников/образа, с которой сделана копия. Для восстановления нужна
эта версия приложения либо совместимая более новая версия с цепочкой миграций.

## Создание копии

```bash
bash deploy/backup.sh
```

По умолчанию используется `.env.production` и каталог `./backups`.
Переменные позволяют выбрать другой конфигурационный файл, каталог и проект:

```bash
ENV_FILE=/srv/amergination/.env.production \
BACKUP_DIR=/srv/backups/amergination \
COMPOSE_PROJECT_NAME=amergination \
bash deploy/backup.sh
```

Имя проекта берётся из `COMPOSE_PROJECT_NAME` или настроек production Compose;
по умолчанию это `amergination`. Для изолированной проверки используйте отдельный
`COMPOSE_PROJECT_NAME`, отдельный `.env` и отдельный `BACKUP_DIR`. Скрипты не
выбирают dev Compose и не обращаются к опубликованным портам PostgreSQL.

**Во время копии есть короткая пауза:** скрипт останавливает `proxy` и `app`,
дожидается завершения текущих запросов, снимает PostgreSQL и аватары, затем
запускает только сервисы, которые работали до копирования. Так загрузка или
удаление аватара не разрывает связь между файлами и БД. PostgreSQL и Redis
продолжают работать. После ошибки скрипт также пытается вернуть ранее
работавшие `app`/`proxy`; проверяйте его код возврата и сообщения.

Не запускайте миграции или другой процесс, меняющий БД/аватары, параллельно с
копированием. Скрипты блокируют одновременный запуск backup/restore через
`BACKUP_DIR/.operation.lock`; у операций одного проекта должен быть одинаковый
`BACKUP_DIR`.

Перед обновлением приложения сделайте копию. Для MVP разумно дополнительно
делать ежедневную копию в удобное время. Расписание пока не устанавливается
автоматически. Успешный запуск считается проверенным только после тестового
восстановления в отдельный Compose-проект.

## Хранение вне сервера

Копия на том же диске не защищает от потери VPS. Скопируйте **весь каталог**
успешной копии в отдельное защищённое хранилище или на другую машину, например
через SFTP. Передача и доступ к хранилищу должны быть защищены; в БД есть
персональные данные и хэши паролей. Используйте шифрование хранилища/архива.
Автоматическая выгрузка и очистка старых копий пока не настроены.

После передачи можно проверить целостность на Linux:

```bash
cd /path/to/20261022T120000Z-XXXXXXXX
sha256sum --check SHA256SUMS
```

Контрольная сумма обнаруживает повреждение при хранении/передаче, но не
подтверждает подлинность. Восстанавливайте только собственные доверенные копии:
дамп PostgreSQL содержит SQL, который будет выполняться в вашей базе.

## Восстановление

1. Выберите нужный Compose-проект и `.env.production`. Сохраните свежую копию
   текущего состояния, если оно ещё доступно. Скачайте полный каталог снимка.
2. На новом сервере создайте конфигурацию, соберите совместимый образ и
   запустите только инфраструктуру:

   ```bash
   docker compose --env-file .env.production -f compose.production.yaml up -d --wait postgres redis
   ```

3. **Смените `SECRET_KEY` в локальном `.env.production` перед восстановлением.**
   Это аннулирует ранее выпущенные JWT, в том числе если Redis был потерян.
   Сгенерируйте новый случайный секрет не короче 32 символов и сохраните его
   только в конфигурации. Пользователи войдут заново.
4. Запустите восстановление с обязательным явным флагом:

   ```bash
   ENV_FILE=/srv/amergination/.env.production \
   BACKUP_DIR=/srv/backups/amergination \
   COMPOSE_PROJECT_NAME=amergination \
   bash deploy/restore.sh /srv/backups/amergination/20261022T120000Z-XXXXXXXX --confirm-restore
   ```

Без `--confirm-restore` скрипт ничего не останавливает и не меняет. До остановки
он проверяет наличие всех файлов, точный формат манифеста, SHA-256, формат
дампа, безопасность архива аватаров и наличие записанной ревизии Alembic в
образе приложения. Затем останавливает `proxy`/`app` и создаёт случайную
промежуточную БД `amergination_restore_<случайный суффикс>` из `template0`.
Дамп восстанавливается **в эту чистую БД** в одной транзакции. Посторонние
таблицы и внешние ключи, созданные в рабочей БД после снимка, этому не мешают.
Миграции выполняются в промежуточной БД до переключения приложения.

После успешного восстановления файлов скрипт запрещает новые подключения к
рабочей и промежуточной БД, завершает только их оставшиеся подключения, а затем
в одной транзакции переименовывает текущую БД в
`amergination_previous_<случайный суффикс>`, промежуточную — в рабочее имя и
разрешает подключения к восстановленной БД. Команды выполняются из служебной
БД `postgres`, а не из переименовываемой базы. Рабочее имя берётся только из
`POSTGRES_DB` выбранного Compose-проекта; `postgres`, `template0` и `template1`
в качестве имени приложения запрещены. SQL-идентификаторы экранируются
целиком, имена промежуточных БД генерируются программой.
Настроенная роль `POSTGRES_USER` должна владеть рабочей БД и иметь права
создания и переименования БД. Роль, созданная стандартным образом PostgreSQL
для этого production Compose, имеет необходимые права.

Старая БД **не удаляется**: её имя выводится после переключения, подключения
к ней выключены. Это резерв для ручного отката, а не постоянная резервная
копия. После проверки новой БД и внешней копии администратор может удалить
старую БД отдельно, проверив её точное имя. Автоматической очистки нет;
места на диске должно хватать на две БД и распаковку аватаров.

При обычном SQL-исключении до завершения переключения транзакция откатывает
оба переименования; helper сверяет OID БД и пытается вернуть прежние параметры
разрешения подключений. Сбой процесса, потеря соединения во время commit или
выключение сервера могут потребовать ручной проверки имён и `datallowconn`.
Не считайте сообщение об ошибке гарантией того, что имя уже переключено либо
ещё не переключено. Во всех таких случаях сайт остаётся остановлен.

В конце запускается `up` приложения с текущей конфигурацией, включая новый
`SECRET_KEY`. Пользователям не открывается неподготовленная промежуточная БД.

Архив аватаров принимает только обычные PNG-файлы с генерируемыми именами в
одном каталоге `avatars/`. Абсолютные пути, `..`, вложенные каталоги, ссылки,
повторы имён и специальные файлы запрещены. Ограничения: до 100 000 файлов,
до 2 МиБ на файл и до 10 ГиБ суммарно. Распаковка выполняется в закрытый
временный каталог; существующие файлы заменяются только после полной проверки.
`extractall()` и рекурсивное удаление не используются.

Аватары, созданные после выбранной копии и отсутствующие в ней, сохраняются
как лишние файлы. Восстановленная БД на них не ссылается. Автоматической очистки
таких файлов нет. После неудачной распаковки может остаться закрытый каталог
`.restore-...`; он не включается в последующие копии.

Если восстановление после остановки завершилось с ошибкой, `app`/`proxy`
остаются остановлены. БД и файловый volume не образуют общую транзакцию:
устраните причину и повторите проверенное восстановление перед запуском сайта.
Оставшиеся `amergination_restore_...` и `amergination_previous_...` не удаляются
автоматически. Их точные имена выводятся для проверки; перед ручным откатом
сначала убедитесь, какая БД сейчас имеет рабочее имя. Для отката переименовывают
нужные базы из подключения к `postgres` при остановленных `app`/`proxy`,
затем явно разрешают подключения к выбранной рабочей БД. Не удаляйте базы
по совпадению префикса и не выполняйте откат через безусловный `DROP DATABASE`.
Если образ не понимает восстановленную ревизию Alembic, миграции завершатся
ошибкой и приложение не будет открыто пользователям.

После успеха проверьте `/health/ready`, вход в аккаунт, историю просмотра и
открытие аватара. Также проверьте код возврата скрипта и логи приложения.

## Redis и сессии

Redis не входит в этот комплект копии. Production Compose хранит AOF в
собственном persistent volume `redis_data`; обычный перезапуск его сохраняет.
Не удаляйте volume при перезапуске или обновлении. При потере сервера кэш
можно заполнить заново, но вместе с Redis теряются записи отзыва токенов и
ограничений частоты. Поэтому при disaster recovery нужна описанная выше
смена `SECRET_KEY` до запуска приложения. Пароли пользователей в PostgreSQL
при этом сохраняются.

Справка PostgreSQL 17: [CREATE DATABASE и чистый template0](https://www.postgresql.org/docs/17/sql-createdatabase.html),
[ALTER DATABASE: переименование и управление подключениями](https://www.postgresql.org/docs/17/sql-alterdatabase.html).
